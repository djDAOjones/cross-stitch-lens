# M11 — Advanced grid and tick controls

## Outcome

Provide practical, preset-led control over preview and printed chart furniture:
minor/major grids, border, ticks, numbering, coordinates, placement, and
high-contrast print styles. Users can obtain standard results quickly without
turning the panel into a wall of controls.

## Current baseline

The persisted `GridStyle` covers show/hide, minor and major intervals, colour,
minor/major integer thickness, ticks, and tick-font pixels. The same mutable
style drives the preview overlay, chart PNG, and PDF chart raster. Grid geometry
(`gridLines`, `snapSpan`, `tickLabels`) is shared and tested, but print and screen
units are conflated: CSS/device pixels in preview become chart-raster pixels at
export. Opacity, outer border, line pattern/join, empty-cell visibility, grid
layer, edge-specific ticks, numbering origin/direction, and presets do not exist.

## Recommended model

Keep geometry and visual style separate. A compact model might contain:

- divisions: minor/major intervals and visibility;
- lines: width, colour, opacity, solid/dashed treatment, border treatment;
- coordinates: tick/number interval, start/origin, enabled edges, direction;
- typography: print-safe family, size, weight, orientation, and offset;
- layering: above/below colour and empty-cell behaviour;
- target overrides: preview versus pattern export where physical units differ.

Do not copy the long requirements list directly into flat UI controls. Define a
small set of immutable presets (“Fine”, “Every 10”, “Traditional”,
“High-contrast print”, “No grid”), let applying one populate visible values,
and show “Custom” after an edit. Advanced disclosure should follow the Carbon
accordion/progressive-disclosure pattern and remain navigable in M6's narrow
layout.

The project file should store canonical style values, not only a preset name.
Preset identity is useful provenance but cannot be the sole source because
presets may evolve. Separate preview-only preferences from the durable print
design deliberately; the current accidental sharing is not a persistence rule.

## Geometry and rendering questions

- Are intervals measured from grid origin and are boundary lines always major?
- Do coordinate numbers label stitch centres, grid boundaries, or both?
- How do reversed axes and non-one start values appear in the key/page ranges?
- Are thicknesses CSS px on screen and points/mm in print, or semantic tokens
  resolved per target?
- What does “below stitch colours” mean when colour cells are opaque?
- How are dashed lines aligned across tiled M10 pages?

Resolve these with pure geometry examples before adding canvas branches.

## Likely implementation surface

`src/worker/grid.ts`, `src/ui/preview.ts`, `src/export/chart.ts`, PDF furniture,
controls/CSS, project schema/migration, and grid/export tests. Keep the shared
geometry pure while target renderers resolve units and colour tokens.

## Acceptance evidence

Test every preset, custom transitions, interval boundaries, all enabled edges,
origins/directions, tiny grids, transparent cells, scale/DPR changes, project
round trip, and preview/export target separation. Use pixel-level tests only for
stable geometry; manual/visual regression evidence should inspect light/dark UI,
grayscale and high-contrast print, 200% reflow, minimum cell sizes, large page
tiles, and keyboard/screen-reader operation.

## Dependencies and risks

- Coordinate and line geometry must compose with M9 symbols and M10 pagination.
- Excess customisation is a discoverability and narrow-panel risk.
- Persisted schema growth needs migration defaults matching today's appearance.
- Colour-only grid distinctions cannot be the only meaning.
