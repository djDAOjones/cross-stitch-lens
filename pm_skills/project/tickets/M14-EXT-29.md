## Two readings

**Reading A (recommended).** "Threadify colours" is the
**full-RGB↔threads** switch — the boolean today's `Colour mode`
select carries — and "Constrain number of colours" is the count
switch (today's `Limit colours`). Coherent with memo 14, where
`Colour mode` is replaced outright: its on/off role must land
somewhere, and a leading "Threadify colours" switch is that
somewhere. Anatomy: Threadify switch → count switch → Colours
slider+input+steppers → (M15: Colour profile select).

**Reading B (literal).** The existing `Limit colours` switch renames
to "Threadify colours" and moves first; the later "constrain number
of colours" toggle is then the same control named twice — internally
inconsistent, which is why A is recommended. Recorded so the gate
conversation starts from the owner's words, not my paraphrase.

## Fixed regardless of reading

- **Colours control grows steppers**: slider + number input (both
  exist, D92/D98) + increment/decrement buttons, all in lockstep,
  announced once per change, 44 px targets on the steppers.
- **`Use exactly this many` retires.** Its semantic (exact vs
  maximum count) either collapses to one behaviour or is explicitly
  cut: decide whether the constrain switch means "at most n" (today's
  default) with exact gone entirely, or "exactly n". State the answer
  in the decision entry; the policy layer supports both, so this is
  naming, not engine work.
- Default stays **eight** with the switch on (D98).
- "Threadify" is a coinage — sentence-case it as "Threadify colours"
  and let the pick gate confirm the owner wants the word on the
  surface (it is memorable but not "user language, not implementation
  terms"; the owner coined it, which is its own justification).
