# M9 — Symbols and practical chart modes

## Scope signed 2026-08-11 (D160)

The four owner decisions are made; the sitting happened in-session on
the agent's recommendations, accepted whole:

1. **Visual language: app-owned vector shapes.** No font asset, no
   fontkit dependency, one geometry model for the canvas chart and the
   PDF (pdf-lib `drawSvgPath`). A **reviewed set of ~64 glyphs**
   (matching the colour slider's ceiling), drafted and signed in
   batches through the gallery process (D139/D146 precedent), judged at
   print size. Past the set, symbol export **refuses with a clear
   message** — repeating a symbol silently stays banned.
2. **Licence: dissolved by decision 1.** Nothing is embedded, so M9 is
   distribution-independent and **decoupled from ICE-TAURI-01** — the
   spike returns to being a capture/packaging investigation. The
   standard-font route died on machine-dependence (the chart raster
   uses system fonts) and the embedded-font route on the fontkit
   dependency + licence surface.
3. **Manual overrides: collisions unrepresentable, not validated.**
   Pick from *unused* symbols only; taking another thread's symbol is
   an explicit swap, never a conflict state. No free-text or arbitrary
   Unicode, ever. The model persists `threadId → symbolId` overrides
   from day one; the override UI is a v1-optional slice.
4. **Persistence: symbols follow identity, never colour, and
   assignment is state, not recomputation.** Keyed on
   `brandId:reference`; a thread present before and after a palette
   change keeps its symbol; reorder and hide cannot move anything.
   First need takes the next unused symbol from the canonical order and
   is **stored in the project file** — determinism and stability fall
   out of persistence. Departed threads release to the *back* of the
   queue; dormant overrides stay in the file. Cross-brand replacement
   resets assignments — no RGB-similarity carryover (D55/D56).
   Adjacency/similarity optimisation is out of scope for v1: initial
   assignment only, later, data-driven, never a re-shuffle.

## Outcome

Turn the existing colour chart into a pattern that remains usable when printed
without colour. Every used thread has one stable, unique, legible symbol; the
same assignment appears in chart cells and keys across PNG/PDF exports and after
project reload.

## Current baseline

`src/export/chart.ts` renders enlarged output colours plus grid lines and numeric
ticks to one raster canvas. `src/export/pdf.ts` embeds that chart PNG and draws a
vector title/key using pdf-lib's Helvetica standard fonts. The key contains a
swatch, thread code when available, and hex value. There is no symbol model,
assignment algorithm, symbol asset, chart-mode selector, or per-thread identity
buffer. M7 must first make thread identity survive the processing output;
RGB-only reverse lookup cannot distinguish two references with the same RGB.

## Model and assignment boundary

Treat symbols as stable asset identifiers, not arbitrary Unicode characters or
font-dependent display text. Define a reviewed symbol set whose glyphs can be
rendered consistently to canvas and PDF. Candidate approaches are:

- small vector paths/primitives owned by the app;
- an embedded, redistributable font with documented licence and pdf-lib support;
- a deliberately limited standard-font set only if print tests prove adequate.

The existing PDF standard fonts are WinAnsi-limited; `toWinAnsi` deliberately
replaces unsupported characters. Relying on the operating system's symbol font
would make exports machine-dependent. Asset licensing and PDF embedding are
therefore part of this milestone, not polish.

Persist assignment by stable thread identity from M7. Automatic assignment must
be deterministic, unique within a chart, and stable when unrelated palette
entries are reordered or hidden. Manual overrides need uniqueness validation and
an explicit conflict state. “Avoid visually similar symbols for adjacent
colours” is an optimisation objective: define symbol-similarity groups and
colour/thread adjacency from the stitch grid, then prefer separated groups for
high-frequency neighbours. Never claim an optimal solution unless proven.

## Chart modes

Support three explicit modes sharing one geometry model:

- colour cells;
- black-and-white symbols;
- symbols over colour.

Symbols must be centred per stitch, scale with the chosen cell size, meet print
contrast against their background, and remain recognizable after PDF/PNG
rasterisation. Empty cells receive no thread symbol. The key should show symbol,
brand/reference, name, swatch where relevant, and stitch count. Keep screen
preview styling and print styling distinct where M11 requires it.

## Likely implementation surface

A pure symbol catalogue/assignment module under `src/core/`, M7's indexed output
or equivalent identity data, project schema/migration, chart geometry/rendering,
PDF font/vector assembly, Pattern Export controls, and stats/key generation.
Avoid DOM or pdf-lib imports in `src/core/`.

## Acceptance evidence

Test deterministic assignment, palette reorder, added/removed unused threads,
duplicate-RGB identities, manual conflicts, more used colours than symbols,
transparent cells, adjacent similar-colour regions, and save/load round trip.
Inspect every chart mode at minimum/typical cell sizes on screen, exported PNG,
and printed PDF. Check grayscale, low-ink printing, key/chart agreement,
multi-page readiness, keyboard controls, and non-Latin project titles.

Decide and document failure when the used-colour count exceeds the reviewed
symbol set; repeating a symbol is not an acceptable silent fallback.

## Dependencies and open decisions

- Depends on M7's stable thread identities and usage counts.
- Should precede symbol-aware M10 multi-page charts.
- Owner decisions: symbol visual language, permitted asset/font licence, manual
  assignment scope, and whether symbol assignments survive palette replacement.
