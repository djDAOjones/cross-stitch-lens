# M12 — Fabric sizing and thread estimation

## Outcome

Show useful physical dimensions and qualified per-thread length/skein estimates
that update with the design. Every result exposes its units and assumptions so a
maker can plan materials without mistaking an estimate for a guarantee.

## Current baseline

`computeStats` counts grid cells, non-empty stitches, empty cells, and stitches
per distinct RGB; it attaches the first matching palette code/name. Physical
dimensions, fabric count, fabric margin, strand count, stitch-length model,
waste/allowance, and skein length do not exist. M7 must establish stable thread
identity before per-reference estimates are trustworthy, particularly for
duplicate RGB entries.

## Fabric model

Store fabric count as stitches per inch, matching common Aida terminology.
For a design `gridWidth × gridHeight`:

```text
design inches = stitches / fabric count
cut size = design size + 2 × finishing margin
centimetres = inches × 2.54
```

Keep design size and recommended cut size distinct. Let users choose displayed
units without converting and re-saving the canonical count repeatedly. State
whether stitching is “over one” fabric square; other fabric/over-two models are
future explicit modes, not hidden factors. Provide common count choices plus a
validated custom positive value.

## Thread estimate model

Separate auditable components:

1. **Front cross geometry:** two diagonals per full cross. For square pitch `p`,
   ideal front length per stitch is `2 × sqrt(2) × p`.
2. **Back travel and path overhead:** depends strongly on stitch order and
   grouping. A simple per-stitch multiplier is an estimate, not measured routing.
3. **Start/finish and waste allowance:** explicit length or percentage per
   colour, especially important for sparse colours.
4. **Working strands:** convert stitched strand-length to purchased floss
   consistently; document how six-strand floss split into the chosen working
   strand count is modelled.
5. **Skein length and rounding:** configurable catalogue metadata with a
   documented default, then round required skeins upward.

Do not bury these choices in a single magic constant. A first implementation can
use a clearly named conservative multiplier and allowance, but the UI and export
must disclose them. “Approximately” and an assumptions summary are part of the
result.

## Data and UI boundary

Use an identity-indexed stitch count supplied by M7 rather than remapping RGBA in
the UI. Pure calculation inputs should include grid dimensions, fabric count,
margin, working strands, skein length, routing multiplier, and waste allowance.
Outputs should include design/cut dimensions, total estimate, per-thread
estimate, skeins rounded up, and warnings for full-RGB/off-palette output.

Project persistence should keep design-specific fabric and estimation settings.
Display-unit preference may be shell-level if it does not affect results.
Inventory could later subtract owned skeins, but M12 should not silently merge
planning estimates with M7 stock counts.

## Likely implementation surface

A pure estimator near `src/core/stats.ts`, identity-aware stats, Info/Pattern
Export UI, project schema/migration, chart/PDF key and project summary, plus unit
and round-trip tests. Keep manufacturer package lengths as data, not branches in
the formula.

## Acceptance evidence

Test hand-calculated grids, empty designs, one stitch, sparse versus dense
colours, several fabric counts, inches/cm display, zero/invalid settings,
different strand counts, exact-skein boundaries, rounding, and duplicate-RGB
identities. Confirm updates after grid/palette/source changes, project round trip,
and consistency among info panel, PDF key, and exported summary. Have an
experienced stitcher review whether defaults and wording are useful before
sign-off.
